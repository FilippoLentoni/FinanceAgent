# Traditional portfolio MCP and research lifecycle

Beta has an independent traditional-optimization MCP Gateway in addition to the existing PPO Gateway. The LangGraph runtime discovers both with the caller's bearer token. Classical tools cannot silently fall back to PPO. Both endpoints use the existing beta Cognito identity configuration. Endpoint references are `/finplan/beta/financeagent/agent/gateway-endpoint-ref` and `/finplan/beta/financeagent/agent/classical-gateway-endpoint-ref`.

Ask the hosted agent:

- “Compare PPO and traditional portfolio planning recommendations today.”
- “Give me the mean-variance portfolio recommendation today.”
- After a traditional recommendation: “Why should I sell Google?”
- “Why did the traditional recommendation change since yesterday?”
- “Are we trending green or red, and why?”
- “Review recent portfolio optimization literature and our performance feedback.”
- “Accept this recommendation.” Review the returned exact paper decision, then confirm it.
- “Reject this recommendation.” Confirm the rejection; the saved holdings remain unchanged.
- “Retrieve the last three portfolios and market snapshots.”

Direct MCP clients discover the same versioned skill recipes in tool descriptions, including instruction checksums. Skills are instructions, rather than separate executable MCP endpoints. Hosted responses record selected skills and actual tool calls; `answer.portfolio_analyses` contains the numerical producer records. The hosted portfolio workflow formats and checks these records without another LLM call; the direct MCP response is the original structured evidence.

| Question | Producer tools | Evidence and limits |
|---|---|---|
| Today's plan and why | `recommend_portfolio` or `recommend_classical_portfolio`, `get_portfolio_decision`, `explain_portfolio_decision` | Frozen PPO replay or traditional objective counterfactuals, Shapley and binding constraints. Issued saved-book recommendations return `decision_id`. |
| What changed between plans? | `list_portfolio_decisions`, `compare_portfolio_decisions` | Distinct stored market dates, holdings revisions, model identity and targets. Comparable traditional models support grouped Shapley; PPO changes are descriptive with frozen replay, without invented feature attribution. |
| How is the plan materializing? | `evaluate_portfolio_decision`, `research_market_events` | Approved observed prices, contiguous accepted holdings revisions, recorded paper fills/costs, target-allocation benchmark and dated external context. Missing accounting, broker actuals and calibrated forecasts are explicit. |
| Accept/reject and tomorrow's holdings | `get_portfolio_decision`, `resolve_portfolio_decision` | Exact human-confirmed resolution; acceptance records fractional simulated fills at the stored reference prices and one new revision. Rejection does not change holdings. Stale market or holdings revisions fail without applying. |
| Last three portfolios and inputs | `get_portfolio_history`, `list_portfolio_decisions`, `list_market_snapshots`, `list_agent_activity` | Durable newest-first holdings/decision/snapshot joins and sanitized tool/agent receipts, independent of expiring conversation checkpoints. |
| Research and feedback | `research_portfolio_models`, `submit_portfolio_feedback`, `run_portfolio_research` | Persisted evidence links, literature metadata, bounded sandbox benchmarking, and proposals requiring review before activation. |

The infrastructure pipeline stores approved market snapshots and the saved paper book. Existing weekday ingestion schedules retrieve completed daily market data, store raw/curated/snapshot artifacts in S3 and publish metadata in DynamoDB. Recommendation requests read these approved snapshots; they do not download live intraday prices. The Model pipeline deploys optimizer/controller code. The Tools pipeline deploys Lambda adapters. The Agent pipeline resolves same-environment manifests and tool targets, then deploys both MCP Gateways and the runtime. Beta talks to beta throughout. The expanded beta target handoff uses a validated Resolve JSON configuration artifact to remain within the CloudFormation action's parameter override limit.

Recommendations persist exact solve inputs, implementation identity, settings, holdings context, outputs and checksums. The Platform owns immutable issued decisions, accepted/rejected resolutions, holdings history and sanitized activity artifacts in dedicated S3 prefixes with DynamoDB indexes. The Model owns numerical explanation/comparison/performance analyses. Explanations reproduce frozen evidence even after holdings change. Issuance does not update holdings or select a production strategy. Accepted decisions do update the saved paper book used by tomorrow's inference. Historical hypothetical comparisons are labeled; the system does not invent a recommendation issued yesterday. Legacy `ca_*` analyses remain readable with the existing classical tools; accepted-book accounting uses the new `pd_*` decision workflow.

Beta raw/curated data, snapshots, plans and reports have no automatic current-object expiry, so decision inputs remain available for future postmortems. Completed hosted turns archive the prompt, checked narrative, exact skill versions/checksums, tool outcomes, confirmation and release identity. Each MCP tool invocation independently archives sanitized inputs/results and successful/failed outcome; credentials and private download grants are redacted. CloudWatch and conversation checkpoint expiry remain bounded. Financial decisions use record identifiers and checksums, rather than treating S3 object versioning as the portfolio version history.

Reading activity history does not recursively copy old archives into each new archive. Audit-history receipts and hosted checkpoints retain the returned immutable event IDs, checksums, metadata and pagination; original evidence payloads stay in their existing durable records. Hosted history narration presents these joins concisely. Direct MCP history reads return original full records that fit the response cap. Larger payloads arrive as explicit canonical-JSON fragments with UTF-8 byte offsets, total bytes and a payload checksum; following `next_token` reconstructs the exact original payload before advancing to older events. Cursors bind the portfolio/session and immutable event checksum. Recommendation and other non-history turn narratives/tool evidence remain stored in full.

The hosted protocol for acceptance is `{ "prompt": "Accept pd_<issued-id>", "stream": false }`, followed in the same session by `{ "action": "confirm", "approve": true, "stream": false }`. The first response has `status=awaiting_confirmation`, `confirmation.paper_decision` and the exact proposed resolution arguments. A cancelled confirmation records the interaction but does not resolve the decision. A separately confirmed rejection records status `rejected`. Direct clients call the resolution tool only after equivalent human review with `confirmed_by_user=true`, the issued holdings revision and a stable idempotency key. Both Gateways propagate `X-Finplan-User-Token` for resolution; the adapter verifies a real public-client Cognito access token and a permitted signed user group. CI tokens cannot resolve paper decisions.

The optimizer defaults are configuration, rather than a claim that experimentation selected the best strategy: 60 completed returns, Ledoit-Wolf covariance, fixed cash 0, maximum instrument weight 0.6, horizon 21 sessions, risk aversion 2, CVaR alpha 0.9, and a proportional turnover proxy. Fixed cash avoids an all-cash minimum-variance solution. Historical mean/covariance and linearly horizon-scaled daily scenarios are modeling assumptions, not calibrated forecasts. The trade Shapley game uses algebraic partial-trade portfolios; infeasible hybrids are disclosed and are not executable plans. Its objective attribution differs from risk allocation or real-world causal explanation.

Green/red refers to the stated observed paper PnL threshold (zero), with separate issued-allocation and implementation-gap trends. A newly issued plan has no forward observations yet. A supplied hypothetical allocation has no observed account ledger. Planned allocation-hold returns are distinct from daily reoptimization and from actual fills. News is dated context, not proof that an event caused a price change.

The weekly beta schedule runs Monday at 09:00 America/New_York. It gathers stored feedback, performance discrepancies, prior experiment findings and literature metadata, then requests one existing sandbox CPU benchmark. The initial supported search covers three traditional families and three lookbacks with cash, buy-and-hold and equal-weight controls. Maximum runtime is 900 seconds; hard estimated cost limits are $0.50 per week, $2 per month and the existing $50 project budget. Duplicate/overlap checks, conditional week claims, CPU-category admission and project budget checks precede paid work. Literature and feedback are untrusted evidence. New code, features and algorithms remain proposals; the controller runs only supported reviewed configurations. Results feed the next review. Strategy replacement requires explicit reviewed activation and fresh forward validation.

The implementation round has a separate $5 incremental cap. Billing estimates are conservative and AWS Budgets reports can lag. Verification receipts, deployment revisions, bounded job results, isolation checks and final cost accounting are recorded separately in the beta acceptance report. Human login/client onboarding is not established by machine-principal tests.

User-triggered paid research first returns an estimate; repeating an explicit launch request then presents the exact paid tool call for confirmation. The classical MCP passes a separately verified Cognito access token through its allowed `X-Finplan-User-Token` header. Direct clients must send this header with the same raw token used in Authorization for paid research. Read-only calls need only normal MCP authorization. Caller-supplied role/group arguments do not grant access.
